용인 구조화 데이터LocalBusiness 구조화 데이터리치 결과 테스트JSON-LD

용인 구조화 데이터 작업의 핵심은 새 정보를 만드는 것이 아니라, 홈페이지 화면에 이미 적힌 가게 이름 · 주소 · 전화 · 영업시간을 검색엔진이 읽는 형식으로 한 번 더 적는 일입니다. Google 문서상 LocalBusiness의 필수 속성은 이름(name)과 주소(address) 두 가지뿐이고, 나머지는 권장입니다. 다만 화면에 없는 내용을 데이터에만 넣으면 안 되고, 올바르게 넣어도 검색 결과에 특별한 모양으로 나온다는 보장은 없습니다.

핵심만 먼저
  • LocalBusiness 구조화 데이터의 필수 속성은 name(가게 이름)과 address(실제 위치) 두 가지입니다.
  • 전화번호(telephone)는 국가 코드와 지역 번호를 포함해 적고, 좌표(geo)는 소수점 다섯 자리 이상으로 적습니다.
  • 페이지 방문자에게 보이지 않는 내용을 마크업하지 않습니다. 자기 가게 별점(aggregateRating)은 다른 가게 리뷰를 모으는 사이트에만 권장됩니다.
  • 리치 결과 테스트(URL 또는 코드 붙여넣기)로 오류를 고친 뒤 URL 검사 도구로 Google이 페이지에 접근할 수 있는지 확인합니다.

1구조화 데이터를 넣으면 가게 홈페이지에서 무엇이 달라지나요?

구조화 데이터는 사람이 읽는 화면 글과 별도로, 검색엔진에게 '이 페이지는 이런 가게의 정보다'라고 정해진 형식(schema.org)으로 알려 주는 코드입니다. Google 검색 센터는 이 데이터를 넣으면 검색 결과에서 특별한 기능을 쓸 수 있게 된다고 설명합니다.

기대치는 낮춰 두는 편이 좋습니다. Google의 일반 가이드라인은 마크업이 올바르더라도 리치 결과 표시가 보장되지 않는다고 적고 있습니다. 구조화 데이터는 노출을 사는 장치가 아니라, 이미 정확한 가게 정보를 오해 없이 전달하는 장치입니다. AI 검색과의 관계는 세종 AI 검색 노출 글에서 따로 정리했습니다.

2LocalBusiness에는 어떤 항목을 적나요?

Google 문서의 '로컬 비즈니스' 항목을 사장님이 실제로 채울 값으로 옮기면 아래와 같습니다. 필수는 두 줄뿐이고, 나머지 권장 항목은 화면에 있는 것만 골라 넣습니다.

속성구분무엇을 적나주의할 점
name필수간판과 같은 가게 이름홍보 문구를 붙이지 않음
address필수PostalAddress 형식의 실제 위치하위 항목(시 · 구 · 도로명 · 우편번호)을 가능한 한 많이
telephone권장손님이 거는 대표 번호국가 코드와 지역 번호 포함(예: +82로 시작)
openingHoursSpecification권장요일 · 여는 시각 · 닫는 시각시각은 hh:mm:ss, 계절 영업은 validFrom · validThrough
geo권장위도 · 경도소수점 다섯 자리 이상
url권장그 지점 페이지의 전체 주소실제로 열리는 링크
menu · servesCuisine권장(음식점)메뉴 페이지 주소 · 음식 종류메뉴는 전체 URL로
priceRange권장가격대 표시100자 미만, 화면 표시와 같게
유형은 되도록 구체적으로 고릅니다. Google은 LocalBusiness보다 Restaurant처럼 더 좁은 하위 유형을 쓰라고 안내하고, 여러 업종을 함께 하면 유형을 배열로 적을 수 있다고 설명합니다(additionalType은 지원하지 않음).

3용인처럼 구 · 읍 · 면이 나뉜 도시는 주소를 어떻게 적나요?

1,112,301명용인시 인구('26. 8월말, 용인시 기본현황)
3구 5읍 2면 32동용인시 행정구역(용인시 기본현황)

용인특례시 누리집의 기본현황을 보면 '26년 8월말 인구가 1,112,301명이고, 행정구역은 처인구 · 기흥구 · 수지구 3개 구 아래 5읍 2면 32동으로 나뉩니다. 같은 동네 이름이나 비슷한 상호가 여러 구에 있을 수 있는 규모라, 주소를 '용인'까지만 적으면 손님도 검색엔진도 헷갈리기 쉽습니다.

  • 화면의 '오시는 길'에 구 이름까지 들어간 도로명주소를 먼저 적습니다.
  • 구조화 데이터의 주소는 그 글자를 그대로 옮깁니다. 화면은 '기흥구'인데 데이터는 '용인시'로만 끝나는 식의 차이를 없앱니다.
  • 읍 · 면 지역 가게는 도로명주소와 함께 우편번호도 채웁니다. 하위 항목을 많이 채우라는 것이 Google 안내입니다.
  • 좌표는 지도 앱에서 가게 입구를 찍어 소수점 다섯 자리 이상으로 가져옵니다.

4화면에 없는 내용을 데이터에만 넣으면 왜 안 되나요?

Google의 구조화 데이터 일반 가이드라인은 '페이지 독자에게 표시되지 않는 콘텐츠를 마크업하지 않는다'를 첫 원칙으로 둡니다. 오해를 주는 내용, 소유 관계를 왜곡하는 내용도 금지이고, 문제가 있으면 직접 조치(수동 조치)를 받아 리치 결과 자격을 잃을 수 있습니다. 이 경우 웹 검색 순위 자체에는 영향을 주지 않는다고 문서에 적혀 있습니다.

자기 가게 홈페이지에 별점(aggregateRating)이나 리뷰(review)를 넣는 경우가 많습니다. Google 문서는 이 두 속성을 '다른 지역 업체의 리뷰를 모으는 사이트'에만 권장합니다. 우리 가게 별점을 데이터에 직접 적는 것은 피하는 편이 안전합니다.

가장 흔한 어긋남은 영업시간입니다. 휴무일을 화면 공지로만 바꾸고 데이터는 그대로 두면, 검색엔진이 받는 정보와 손님이 보는 정보가 달라집니다. 시간을 고칠 때는 화면과 데이터를 한 번에 고치는 습관을 들입니다.

5넣은 다음에는 어떤 순서로 확인하나요?

  1. 리치 결과 테스트 열기 — 페이지 전체 주소를 넣거나, 아직 올리기 전이면 '코드'를 골라 붙여 넣습니다. 기본 검사 환경은 스마트폰입니다.
  2. 치명적 오류부터 고치기 — 필수 속성 누락은 리치 결과 자격 자체를 없앱니다. 경고는 고치면 좋지만 필수는 아닙니다.
  3. URL 검사 도구로 접근 확인 — robots.txt 차단, noindex, 로그인 요구가 있으면 Google이 데이터를 읽지 못합니다.
  4. 다시 크롤링 요청 후 기다리기 — 새로 바뀐 페이지를 찾는 데 며칠이 걸릴 수 있습니다.
  5. 사이트맵 제출 — 앞으로의 변경도 빨리 알려지게 합니다. 순서는 인천 구글 서치콘솔 글을 참고합니다.
  6. Search Console 보고서 보기 — 리치 결과가 사라지면 구조화 데이터 오류 보고서와 가이드라인을 다시 확인합니다.
자동 테스트는 형식 오류만 잡습니다. '화면과 같은가'는 사람이 눈으로 대조해야 합니다. 홈페이지 주소를 무료 SEO 점검에 넣으면 기본 상태부터 함께 볼 수 있습니다.

6지점이 둘이거나 매장 안에 다른 코너가 있으면요?

Google 예시는 지점마다 별도의 LocalBusiness를 만들고, 각자 그 지점 페이지 주소(url)를 갖게 합니다. 수지구와 처인구에 두 매장을 낸 가게라면 지점 페이지를 따로 두고, 각 페이지에 그 지점의 주소 · 전화 · 영업시간만 적습니다.

한 건물 안의 약국 코너처럼 부서가 있으면 department 속성으로 중첩하고, 부서마다 영업시간과 전화를 따로 적을 수 있습니다. 이름은 일반 부서라면 '가게 이름 + 부서 이름'으로, 부서가 별도 브랜드라면 그 이름만 씁니다.

자주 묻는 질문

구조화 데이터를 넣으면 검색 순위가 올라가나요?

Google 문서는 순위 상승을 약속하지 않습니다. 올바른 마크업도 리치 결과 표시가 보장되지 않는다고 적혀 있습니다. 정확한 가게 정보를 오해 없이 전달하는 장치로 보는 것이 맞습니다.

필수로 꼭 넣어야 하는 항목은 무엇인가요?

LocalBusiness는 name(가게 이름)과 address(실제 위치) 두 가지가 필수입니다. 전화, 영업시간, 좌표, 페이지 주소 등은 권장 항목이며 화면에 있는 것만 넣습니다.

어떤 형식으로 넣어야 하나요?

Google은 JSON-LD, 마이크로데이터, RDFa를 지원하며 JSON-LD를 권장합니다. 보통 페이지의 script type=application/ld+json 태그 안에 넣습니다.

네이버 검색에도 똑같이 적용되나요?

이 글은 Google 검색 센터 문서만 확인했습니다. 네이버가 어떤 유형을 어떻게 쓰는지는 네이버 서치어드바이저 공식 도움말에서 따로 확인하시길 권합니다.
